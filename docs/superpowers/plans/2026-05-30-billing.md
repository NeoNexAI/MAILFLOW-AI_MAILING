# MailFlow PR — Billing (Stripe) + quotas

## Context
Último gran bloque (Fase 5). Pricing (PLAN.md §3.77): Free (1 cuenta, 100
emails/día), Pro $12 (ilimitado), Team $25/usuario. Solo afecta al SaaS; OSS
self-host ignora billing (plan free sin límites duros si se desea).

## Diseño
1. **plans.py (core de negocio en api)**: PLANS = {free, pro, team} con
   `max_accounts`, `max_emails_per_day` (None = ilimitado). Pure, testeable.
2. **Migración 004**: organizations += `stripe_customer_id`, `stripe_subscription_id`.
   `plan` ya existe.
3. **quota.py**: `count_accounts(org)`, `emails_processed_today(org)` (suma
   audit_log.emails_processed de hoy de las cuentas de la org), `can_add_account`,
   `can_process_more`. Enforcement:
   - account-create route → 402/403 si supera `max_accounts`.
   - worker cycle → si supera emails/día, salta con motivo (no rompe).
4. **billing (Stripe), todo guarded por STRIPE_SECRET_KEY**:
   - `app/billing.py`: crear Checkout Session (price por plan), Customer Portal,
     parse de webhook. Si no hay clave → BillingNotConfigured → 501 claro.
   - `routers/billing.py`: `GET /billing/plan` (plan actual + límites + uso),
     `POST /billing/checkout` (devuelve URL), `POST /billing/portal`,
     `POST /billing/webhook` (firma verificada → actualiza org.plan/sub).
   - config: STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, STRIPE_PRICE_PRO,
     STRIPE_PRICE_TEAM, BILLING_SUCCESS_URL/CANCEL_URL.
5. **web**: página `/app/billing` (plan actual, uso vs límite, botón upgrade/portal).
   Dashboard muestra uso. 
6. **docs/.env**: setup Stripe (price ids, webhook secret).

## Verificación
- ruff+format; core sin cambios; api tests: plans (límites), quota (cuenta/uso),
  billing not-configured → 501, webhook firma inválida → 400; alembic 004 up/down;
  web biome+typecheck+build.
- Stripe sin clave: rutas devuelven 501; cuotas funcionan igual. Con claves de
  test (trámite del usuario) el flujo real es operativo.
