# MailFlow PR — OAuth Gmail / Microsoft 365

## Context
Backend + UI + self-host done (PRs #3–#7). Buzones hoy: IMAP + contraseña.
SaaS necesita OAuth2 (sin contraseñas). Deps ya presentes: `msal` (M365),
`google-auth`+`google-auth-oauthlib` (Gmail), `imapclient.oauth2_login` (XOAUTH2).

## Estrategia (mínimo riesgo, máxima reutilización)
Gmail y M365 hablan **IMAP con XOAUTH2** → NO crear providers separados; extender
`ImapGenericProvider` para aceptar `access_token` (usa `oauth2_login` en vez de
`login`). Todo el fetch/move/draft se reutiliza.

## Piezas
1. **core**: `ImapGenericProvider` acepta `access_token: str | None`. Si está,
   usa `oauth2_login(user, token)`; si no, `login(user, password)`. Imap host/port
   por defecto Gmail/M365. Tests.
2. **api `app/oauth.py`**: helpers de OAuth — URLs de autorización, intercambio de
   code→tokens, **refresh** de access_token desde refresh_token.
   - Google: `google-auth-oauthlib` Flow (offline, scope `https://mail.google.com/`).
   - Microsoft: `msal.ConfidentialClientApplication` (scope `IMAP.AccessAsUser.All` + offline).
   - Config-driven (CLIENT_ID/SECRET, REDIRECT_URI). No-op claro si no configurado.
3. **DB migración 003**: `email_accounts.encrypted_oauth` (refresh token cifrado),
   `oauth_email` (dirección). `provider_type` ∈ {imap, gmail, microsoft}.
   password ya no obligatorio para oauth.
4. **api routes `app/routers/oauth.py`**: 
   - `GET /oauth/{provider}/authorize` → URL de consent (state firmado con org).
   - `GET /oauth/{provider}/callback` → intercambia code, crea/actualiza account.
   - Aislado por org vía `require_org` en authorize; callback valida state.
5. **cycle service**: al construir el provider, si `provider_type` es oauth,
   refresca el access_token (oauth.py) y pásalo en vez de password.
6. **web**: onboarding ofrece "Connect Gmail / Microsoft" (botones) además de IMAP.
   `.env.example` + docs (redirect URIs).
